- **Lessons from this whole detour**: (1) don't hand-roll a UI clone of something shown as a reference without first checking whether it's a real shipped feature — check that *before* building an approximation. (2) A `clear`+redraw-on-a-timer bash loop always flickers; redraw in place (cursor-home + overwrite + erase-only-the-tail) instead. (3) In bash, `frame+=$(printf "...\n")` **loses the trailing newline** — command substitution `$(...)` always strips trailing newlines no matter how many are inside; append `$'\n'` explicitly outside the substitution for each line, or lines silently run together. (4) Colored/escape-containing strings must always be *built* via `printf` (e.g. `printf '%b' "$str"`) — plain `var="${COLOR}text${RESET}"` concatenation never interprets the embedded `\033` sequences and prints them as literal text; this is the same bug class hit earlier in the statusline script.
- **Critical macOS bash 3.2 gotcha, found via real PTY testing (2026-07-09):** macOS ships an ancient `/bin/bash` 3.2.57 (frozen since 2007, GPLv3). Its `read -n <N> -t <fractional-seconds>` (e.g. `-t 0.05`) is broken when chained immediately after a prior `read` on the same fd — it returns success (rc=0) having read **zero bytes**, even though the data is already sitting in the pty buffer (proven: the very next loop iteration's fresh `read` picks the same bytes up immediately). This silently broke arrow-key handling entirely (ESC detected, but the following `[`/`A`/`B` bytes were always dropped, so the selector never moved) despite the script looking correct and passing a syntax check. Fix: use an **integer** `-t` value (e.g. `-t 1`) and read all remaining escape-sequence bytes in a single `read -rsn2` call instead of two chained fractional reads — confirmed reliable. General rule for this machine: never chain a `read -t <fractional>` immediately after another `read` on the same terminal fd; use an integer timeout, or read the follow-up bytes in one call.
- **How this was actually verified, not just guessed**: built a Python `pty.fork()` harness (installed `pyte` for a real terminal emulator) to run `dashboard.sh` under a genuine pseudo-terminal, feed it real key bytes (`os.write` on a timer), and render the captured ANSI stream through `pyte.Screen`/`pyte.Stream` to inspect the actual resulting screen line-by-line — this is how the bash 3.2 `read` bug and the "many duplicate idle lines" issue were both confirmed and fixed before reporting back, rather than guessing from reading the script. Reuse this harness (`pty_harness.py`, written to the session scratchpad) for future interactive-terminal-script debugging in this project — it's the only way to catch timing-dependent bugs like this.

- **kitty session-file gotcha**: the `launch` directive's arguments are passed literally, with NO shell expansion at all — not `$VAR`, not `~`. (Kitty's own docs: "Environment variables... are expanded in the session file, except in the *arguments* ... to the launch command.") `cd ~/path` works because `cd` is kitty's own directive with its own path handling, but `launch bash ~/.claude/foo.sh` passes the literal string `~/.claude/foo.sh` to bash, which doesn't exist as a file — always use absolute paths inside `launch` command arguments in `.kitty-session` files.

- **🚨 SEVERE BUG I CAUSED — never repeat (2026-07-09).** My earlier hook did `kitty @ send-text --match id:$KITTY_WINDOW_ID '\x07'` to "ring the bell." **`kitty @ send-text` injects text into the target program's STDIN as if typed — it does NOT write to the screen.** And BEL `\x07` is byte 0x07, which is exactly **Ctrl+G**. Claude Code binds Ctrl+G to "open the prompt in `$VISUAL`/`$EDITOR`". So every `PermissionRequest` and `Stop` hook typed Ctrl+G into Tejas's session, launching **vim** on an empty `/tmp/claude-501/claude-prompt-<uuid>.md`, repeatedly, mid-work. Evidence: 3 stray empty `claude-prompt-*.md` files with mtimes exactly matching hook fires. Removed `agent-hook.sh` + its dead `~/.claude/agent-status/` dir entirely.
  - **Rules learned:** (1) `kitty @ send-text` = keystroke injection into a running program; NEVER use it to produce terminal *output* or side-effect a TUI. To emit a real bell from inside a window, write BEL to the controlling terminal (`printf '\a' > /dev/tty`), or better, use the app's own notification setting. (2) Control bytes are keystrokes: `0x07`=Ctrl+G, `0x03`=Ctrl+C, `0x04`=Ctrl+D, `0x1a`=Ctrl+Z. Sending a "harmless" control code to a TUI's stdin fires whatever that app bound to it. (3) **Check whether the app already supports the thing natively before hooking it** — Claude Code had `preferredNotifChannel: terminal_bell` all along; the whole hook was unnecessary as well as harmful.
- kitty remote control is on (`allow_remote_control yes`, `listen_on unix:/tmp/kitty-{kitty_pid}`) so scripts can open new tabs / focus tabs in the running instance via `kitty @ launch` / `kitty @ focus-tab`. **zsh gotcha hit while writing `projects`:** `local varname` (no `=`) inside a `for` loop body, when `varname` already holds a value from a prior loop iteration (function-scoped locals persist across loop iterations, they're not reset per-iteration), makes zsh print `varname=value` to stdout instead of silently redeclaring — this is zsh's `typeset`-as-query behavior kicking in.
